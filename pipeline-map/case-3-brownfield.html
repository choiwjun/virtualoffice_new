CASE 03 · Brownfield · 역방향 진입

이미 개발된 프로젝트에 적용하기

파이프라인은 원래 기획 → 명세 → 코드 정방향인데, 기존 프로젝트는 코드가 이미 끝점에 있습니다. /reverse가 코드 → 명세를 역추출해 파이프라인 중간에 끼워 넣습니다. 핵심은 /reverse가 만드는 산출물이 /screen-spec이 만드는 것과 동일하다는 점 — 그래서 이후 단계가 그대로 작동합니다.

체인. /reverse scan → extract → review → finalize → specs/ 확보 → (신규 기능은 /socrates·/screen-spec) → /tasks-generator analyze → /auto-orchestrate → /sync
/reverse · 코드에서 명세 역추출 읽기 전용
기존 코드베이스를 분석해 도메인 리소스·API 계약·화면 명세를 자동 추출. Read/Grep/Glob만 사용 — 코드를 절대 수정하지 않음. 4단계로 진행.
4단계/reverse 내부 흐름scan → extract → review → finalize
scan
구조·기술 스택·규모 측정 (LOC, 엔드포인트, 컴포넌트, 테이블, 커버리지)
--verbose
extract
DB/ORM→리소스, 라우트→API, 컴포넌트→화면. 각 항목에 confidence 부여
--domain--screens--api
review
체크리스트로 검수 + 자동 감지 어려운 항목(비즈니스 규칙·엣지케이스) 수동 보완
finalize
_reverse_meta 제거 + 갭 분석(스키마 불일치·기술부채·누락 명세)
--format openapi
/screen-spec과 동일한 specs/ 산출 → ICV 정상 작동▼
specs/ 확보 — 파이프라인 합류 지점
specs/domain/resources.yaml + specs/screens/*.yaml + specs/api/*.yaml. 이 지점부터는 마치 /screen-spec을 막 끝낸 것처럼 표준 파이프라인에 합류.

/auto-orchestrate → /sync
추가 개발 실행. 개발 중간·이후 /sync로 명세–코드 드리프트를 지속 검증(역추출 명세가 코드와 어긋나지 않게).
추출 신뢰도 (confidence) — 역추출은 그대로 믿지 말 것
신뢰도의미조치
0.9 +높음자동 확정 가능
0.7 ~ 0.9중간리뷰 권장
0.5 ~ 0.7낮음수동 확인 필수
< 0.5매우 낮음재작성 권장
신뢰도 요소: 타입 힌트(0.3) · 테스트 커버리지(0.2) · docstring(0.2) · 일관 패턴(0.2) · 명시적 계약(OpenAPI/TS, 0.1).

실무 주의 3가지. ① /reverse는 읽기 전용이라 안전하게 돌려도 됨 · ② confidence가 낮은 명세를 그대로 믿으면 ICV도 틀린 걸 검증하므로 /reverse review 필수 · ③ brownfield는 전체가 아니라 갭 + 신규 기능만 태스크화(전부 잡으면 재구현).
갭. 현재 /stargate(통합 진입)는 신규 위주라 reverse 분기가 없습니다 — 기존 프로젝트는 /reverse를 직접 호출하는 게 맞습니다. 품질 진단만 원한다면 spec 없이 /code-review · /audit · /trinity를 바로 돌려도 됩니다(→ Case 05).
